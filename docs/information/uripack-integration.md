# uripack integration and migration checks

<!-- docs:section purpose -->
## Purpose

Prepare portable uriprocess candidates from immutable source selections and use
the real uripack planner and guarded executor for their extraction. This is the
local integration contract of `subactor/uriprocess`, not an ecosystem migration
or production cutover report. HOME `subactor`; SHAPE `runtime_service`.

<!-- docs:section scope -->
## Scope

The POA selection contains `ticket-currency` and `ticket-readiness`
from `subactor/runtime` revision
`cca2880ded7433f89480006d65cc8c3f4b6ad6bf`. Their original
`poa://subactor.com/process/<name>/v1` identities remain unchanged. Original
contracts, implementations and upstream tests are byte-preserving projections.
The adapters, package metadata and Dockerfiles are generated by uriprocess.

The native Python selection adds the complete ticket-lifecycle, account-twin,
LLM Account Hub, managed-tunnel, secret-intake and credential-harvest
connector packages from `subactor/connectors` revision
`ea82418ed593fa78193975b53951459be4e07d51`. These retain their five original files
each: package metadata, tests, Python modules and connector manifest. They add
one `planfile` route, ten exact `twin` query routes and four exact `llm-account`
routes for binding discovery, CLI status, planning and authorized execution,
one tunnel preflight route, two browser intake routes and one grant-gated
harvest route. Their existing package
names, versions, dependencies and `urirun.bindings` entry points are unchanged.
Version 11 added the two Platform packages described below. Version 12 adds
twin-map; the eleven packages cover thirty-one original URI identities. The metadata source
revision identifies the URIprocess implementation base for this change.

The preparation tool explicitly imports the installed `uripack_refactor` package.
It does not discover sibling repositories or load an automated Strategy. It
uses uripack's extraction-plan contract, not a Strategy execution receipt.

## Content

### Prepare and inspect

Use Python 3.11+ and Node 22+. Resolve the intended uripack checkout explicitly.
For this workspace, the implementation is under `./uripack/uripack`, while
`./uripack` itself is an enclosing directory. The tested revision is
`23925ec4b3a5283f51e74b36c4bd33a9cd2820b7`; the command does not enforce that pin
or attest to an arbitrary installed package. Verify the checkout and clean
state before reproducing these results.

From the uriprocess repository, with the required Python dependencies installed:

```bash
export PYTHONPATH=/path/to/uripack/uripack/src
python3 tools/prepare_uripack.py \
  --selection selections/runtime-v1.json \
  --source /path/to/runtime \
  --workspace /private/recovery/uriprocess-run
```

The workspace must not exist and must be disjoint from the source repository.
Preparation reads immutable Git blobs, creates `candidate/`, and calls
`uripack_refactor.planner.build_plan` to write `request.json` and `plan.json`.
It does not create `extracted/`. Preserve the workspace at the same absolute
path until application: source paths and digests are part of the plan.
Failed preparation may leave diagnostic files in this new workspace; use a
fresh path when retrying rather than overwriting it.

Each unit owns one complete candidate package. This avoids assigning the same
source path to multiple uripack units. The readiness implementation included in
currency remains an intentional copy of the same pinned upstream bytes.

### Apply through the protected bridge

After review and configuration of a real operator-protected uripack bridge:

```bash
python3 -m uripack_refactor apply \
  --plan /private/recovery/uriprocess-run/plan.json \
  --guard-config /operator/protected/uripack-bridge.json \
  --out /private/recovery/uriprocess-run/extraction.json
python3 -m uripack_refactor verify \
  --plan /private/recovery/uriprocess-run/plan.json \
  --out /private/recovery/uriprocess-run/verification.json
```

The bridge path above is a placeholder, not an installed configuration.
Guard must independently authorize admission, checks, local publication and
completion. Verification checks bytes and modes; it does not grant authority.
Neither the preparation tool nor its CLI provides a synthetic Guard option.
The native Guard export work on separate uriprocess branches uses a different
contract and is not automatically a uripack bridge.

The resulting package root for currency is:

```text
extracted/packs/poa-ticket-currency-subactor.com-v1/tree/poa/ticket-currency/subactor.com/v1/
```

Run `node bin.mjs`, `npm pack --ignore-scripts` or build the existing Dockerfile
from that package root. uripack's enclosing catalog is a different format from
`uriprocess/catalog.json`; do not replace one with the other. The original
repository and its production consumers are unchanged.

### Reproduce verification

```bash
export PYTHONPATH=/path/to/uripack/uripack/src
export URIPROCESS_SOURCE=/path/to/runtime
make test
make test-uripack
python3 tools/check.py --source "$URIPROCESS_SOURCE" --pack --docker
python3 tools/check.py --root /private/recovery/uriprocess-run/candidate \
  --source "$URIPROCESS_SOURCE"
```

Without `URIPROCESS_SOURCE`, ordinary unit discovery explicitly skips the
integration cases. `make test-uripack` requires it. Without `--source`, the
package checker verifies the local catalog and provenance, but cannot prove
agreement with upstream Git. The forged-provenance regression demonstrates why
the upstream comparison matters even when all local hashes agree.

`--pack` builds archives in the checked root's ignored `dist/`, installs them
offline into temporary directories and runs preserved upstream tests against
the installed implementations. `--docker` runs the same tests against the image
with the test directory mounted read-only. Tests are not added to the published
npm payload or production image.

### Run the real native Guard reference test

The existing native-export implementation lives at consumer revision
`3f107a5825babf1b48c99f287f19fd2128ee5e47`. The new runner reuses those exact
Git objects without merging or rewriting its existing worktree. Its checked-in
compatibility reference selects Guard revision
`edb21301fa4ca059f8108b18913c15f1c89ae979` and the uripack revision above.
The runner extracts only the required consumer files and library trees into
a disposable directory. It does not execute dirty checkout files or inherit
bearer credentials, `PYTHONPATH`, or `PYTHONOPTIMIZE` from the calling shell.
Node 22 and Python's installed JSON Schema/YAML dependencies must be available.

```bash
make test-native-export \
  URIPACK_REPOSITORY=/path/to/uripack/uripack \
  GUARD_REPOSITORY=/path/to/organism-guard \
  NATIVE_OUTPUT=/private/recovery/new-native-export
```

Both repository paths are explicit Git object sources; their current branch
does not select the executed library version. Required commits must already
exist locally. Missing objects fail without fetching, installing dependencies,
or falling back to another revision.

The test exports the two original packages from uriprocess revision
`f76773988ccdccd81725ce93017c66615b84a8fb`. It adds an explicitly test-only
Fastlane policy to a disposable source repository and records that repository's
real commit. It verifies the Guard contract/source digests and the uripack
executor digest, then exercises native planning, admission, execution and
receipt/artifact readback with separate test principals. Temporary credentials,
server state, source snapshots and the HTTP server are removed at completion.

Output is a new private directory containing `exports/`, the two materialized
packages and npm archives, `native.log`, and `verification.json`. The wrapper
independently compares every exported package file against the original Git
objects and rejects a successful-looking report with changed package bytes.
Its receipt binds the four source revisions and the native report/log digests.
Failed runs retain diagnostic output and do not produce a success receipt;
retries use a new output directory.

This is an explicit local reference test, not a deployment command. Neither the
test's separate roles nor a passing native receipt supplies production authority.

### Generate and verify native Python connectors

`selections/connectors-v3.json` selects thirty exact files at the connector revision
above. The historical v1 and v2 selections remain unchanged and reproducible
for the first two and three native connectors respectively; their generated
packages remain byte-identical in v3. Original native versions are retained:
secret-intake is 0.2.0, credential-harvest is 0.1.1 and the other four are 0.1.0.
`tools/generate_native.py` requires the selected URI set to equal the
preserved connector manifest, retains file modes, requires upstream tests and
native urirun entry points, and rejects collisions. It adds only uriprocess
metadata and provenance beside the original files. Output must be new.

The current complete native catalog is generated by `selections/native-v1.json`.
It binds each group to an explicit selection path and SHA-256, retaining the
unchanged connectors v3 selection and adding `selections/platform-v1.json`.
The latter selects twelve original files from Platform revision
`0102f2518e8bc1081447f373783503ab3b8d122f`, including both original test modules
and their `tests/__init__.py` files. The packages retain version 0.1.0 and their
`urirun>=0.4.14` dependency:

| Package | Preserved URI |
| --- | --- |
| `platform-uri-blueprints` | `repo://workspace/uri-blueprints/communications/command/implement` |
| `platform-uri-blueprints` | `repo://workspace/uri-blueprints/project-orchestration/command/implement` |
| `platform-uri-blueprints` | `repo://workspace/uri-blueprints/secret-intake/command/implement` |
| `approved-recipient-email` | `email://approved-recipients/message/command/send` |

The blueprint adapter preserves the existing authenticated Control preflight.
The email adapter preserves its exact-recipient plan, signed one-time grant,
replay checks and deployment-owned SMTP settings. Packaging performs none of
those production effects and changes no runtime binding.

`tools/generate_native_catalog.py` combines explicitly supplied Git repositories.
It rejects changed selection digests, missing or extra source mappings, duplicate
package identities and URI ownership across groups. All groups are staged before
publishing a new output directory; a failed later group cannot expose a partial
catalog. The six existing native packages retain identical bytes and metadata.

```bash
python3 tools/generate_native_catalog.py --selection selections/native-v1.json \
  --selection-root . --source connectors=/path/to/connectors \
  --source platform=/path/to/platform --output /private/recovery/native-candidate
python3 tools/prepare_uripack.py --selection selections/native-v1.json \
  --selection-root . --source-map connectors=/path/to/connectors \
  --source-map platform=/path/to/platform --workspace /private/recovery/native-plan
```

The batch plan covers eight native units and twenty-three native URI routes.
The two POA packages remain in their original catalog. Historical single-source
selections and the separately pinned repository split selection remain
reproducible; they do not silently expand to the new Platform packages.

```bash
python3 tools/generate_native.py --selection selections/connectors-v3.json \
  --source /path/to/connectors --output /private/recovery/native-candidate
python3 tools/prepare_uripack.py --selection selections/connectors-v3.json \
  --source /path/to/connectors --workspace /private/recovery/native-plan
```

The generator creates `native/<connector-id>/v<original-package-version>/` and
`native-catalog.json`. The catalog is a packaging projection, not a new runtime
URI registry. Original versionless route strings do not gain a version suffix.
Native catalog entries are separate from the existing POA decision catalog
because native Python entry points do not use its ticket/context stdin adapter.
The preparation command uses the same real uripack planner as the POA path.
Operational application still requires the protected bridge described above.

```bash
export PYTHONPATH=/path/to/uripack/uripack/src
make test-native-packages \
  URIPROCESS_CONNECTORS_SOURCE=/path/to/connectors \
  URIPROCESS_PLATFORM_SOURCE=/path/to/platform \
  BUILDER_PYTHON=/path/to/python-with-build-setuptools-wheel \
  NATIVE_OUTPUT=/private/recovery/new-native-verification
```

The test interpreter requires pytest, packaging and the existing native runtime
dependency. This validation used `urirun 0.4.200`, satisfying the preserved
`urirun>=0.4.14` requirement. The explicitly selected builder requires `build`,
`setuptools>=69` and `wheel`. The checker downloads nothing: wheel construction
uses `--no-isolation`, and installation uses `--no-index --no-deps` into a new
temporary target. The dependency versions are recorded, not presented as a
resolved lock or a bundled offline dependency set.

`tools/check_native.py` compares source bytes and canonical file modes directly with Git,
requires provenance coverage of every original file, and checks generated
metadata against the preserved pyproject. It runs upstream tests on disposable
source copies, builds wheels, installs them, reruns the original tests away from
the source tree, and loads the installed entry points to compare URI sets.
For the combined catalog, repeated `--source-map REPOSITORY=PATH` arguments
select each provenance repository explicitly. A missing repository cannot fall
back to the other source. `--source PATH` remains available for historical
single-source candidates. Receipts retain each actual source repository and SHA.
Canonical mode means Git's executable distinction, 100644 versus 100755;
local umask or ACL group-write permissions do not change that distinction.
The checker parses JUnit cases instead of treating pytest exit zero as complete
evidence. Empty, skipped, failed, malformed or errored test reports are rejected,
as is a different installed test identity, including a changed parameter ID or
module even when the total count is unchanged. Case order may differ; repeated
identities retain their multiplicity. Successful receipts record each package's
`upstream_test_count`, identity comparison and the relative paths and SHA-256
digests of both preserved JUnit reports. The test-only Guard uses the same
completeness check.
Inherited credentials and pytest plugin auto-loading are excluded from these
subprocesses. Tests replace HTTP with their original fixtures; no Control or
Twin request or SMTP message is sent to production. The source package never receives build,
installation or test-cache files.

Output retains all eight wheels, sixteen private JUnit reports, a private build/test
log, and `verification.json`
with source revisions, dependency versions, route sets and wheel digests.
`URIPROCESS_CONNECTORS_SOURCE` and `URIPROCESS_PLATFORM_SOURCE` must be set to
include all source-dependent cases in ordinary unittest discovery; otherwise
unavailable cases are explicitly skipped. `test-native-packages` requires both
and performs the wheel checks too. `test_native_catalog` adds eight regressions,
including full installed-wheel verification, real Platform URIpack extraction,
catalog reproduction and rejection of source mapping and URI collisions.
Protected OneDev must supply the independently pinned Platform input before this
expanded suite can pass; see its
[input adoption](https://github.com/subactor/onedev-agent/issues/267).

### Prepare separate destination repositories

`tools/prepare_repositories.py` prepares one real URIpack plan per explicitly
named `uriprocess/<repository>` destination. The versioned mapping is
`selections/repositories-v1.json`; it pins the packaging repository at
`0e662bb67364648c41783939749ccfe3c3f7b846` and reads both upstream selections
from that revision's Git objects. Original runtime and connector files still
come from their exact revisions listed above. Dirty selection files in the
packaging checkout cannot change the chosen inputs.

| Proposed repository | Preserved package | URI count |
| --- | --- | --- |
| `uriprocess/ticket-currency` | POA ticket-currency v1 | 1 |
| `uriprocess/ticket-readiness` | POA ticket-readiness v1 | 1 |
| `uriprocess/ticket-lifecycle` | subactor-ticket-lifecycle 0.1.0 | 1 |
| `uriprocess/account-twin` | subactor-account-twin 0.1.0 | 10 |
| `uriprocess/llm-account-hub` | subactor-llm-account-hub 0.1.0 | 4 |
| `uriprocess/managed-tunnel` | subactor-managed-tunnel 0.1.0 | 1 |
| `uriprocess/secret-intake` | subactor-secret-intake 0.2.0 | 2 |
| `uriprocess/credential-harvest` | subactor-credential-harvest 0.1.1 | 1 |

These names are proposed Git repository destinations. Existing URI authorities,
Python distribution names, npm scopes, versions and runtime ownership remain
unchanged. A native connector's routes stay together in its existing package.
This local tool contract does not assert a cross-repository ownership transfer.

```bash
export PYTHONPATH=/path/to/uripack/uripack/src
python3 tools/prepare_repositories.py \
  --selection selections/repositories-v1.json \
  --package-source /path/to/uriprocess \
  --source runtime=/path/to/runtime \
  --source connectors=/path/to/connectors \
  --workspace /private/recovery/new-repository-plans
```

Supply exactly the named source IDs. The new workspace must be disjoint from
all three repositories, including the packaging checkout; its own `.subactor/`
directory is therefore unsuitable. Existing outputs and symlink components are
rejected. Preparation has no Git write, network call or Guard admission step.

The output contains immutable-source candidates, `plans/<repository>.json`,
`repository-selection.json`, and the final `repository-plans.json` index with
21 URI-to-repository mappings, eight plan hashes and expected artifact digests.
The empty `repositories/` parent is reserved for separate guarded extractions.
Each plan includes only one original package and its generated
`repository-targets/<repository>.json` record. That record binds the target
repository, package path, upstream revisions, selection hash and original URI
set into the actual URIpack plan digest. Changing the target record after
planning fails source-drift verification before Guard admission.

All original package paths remain inside URIpack's layout. For example, after
separate guarded application the currency package root is:

```text
repositories/ticket-currency/packs/ticket-currency/tree/poa/ticket-currency/subactor.com/v1/
```

Run native package commands from the index's `package_root` under each plan's
`target_root`. No flattening, import rewrite or universal runtime wrapper is
introduced. The destination record is outside the original package's file set.

The batch index is written only after every selection has exact mapping coverage
and globally unique URI ownership. A failed preparation can leave diagnostic
candidates or individual plans; treat an output without the final index as an
incomplete batch and retry in a new workspace. The index is a local planning
record, not signed publication authority. Operators must review and bind each
actual plan through the protected bridge; never use an index's target string as
authority to create, push or transfer a remote repository.

Apply and verify each reviewed plan through the existing `uripack apply` and
`uripack verify` commands described above, selecting its own plan file. There is
no automatic batch admission: approval of one package does not admit another.
Repository initialization, governance adoption, protected CI, remote publication
and production routing need their own implementation and observed evidence.

```bash
make test-repository-plans \
  URIPROCESS_SOURCE=/path/to/runtime \
  URIPROCESS_CONNECTORS_SOURCE=/path/to/connectors
```

The full Python suite passed 38 tests without skips. Eight new tests cover

The original upstream suites run inside each extraction's test Guard check.
The standalone CLI also produced eight plans and 21 URI mappings without

The generated candidates also passed offline package installation checks:

Native verification receipt SHA-256: `84d8a18be63af7f4d42b15990ed7b067ed8d43781a437a81e9ae0b80d1ad2478`.

### Verify the complete repository batch

Before operational extraction, use `tools/verify_repositories.py` with the
expected mapping supplied independently of the generated batch. The verifier
reconstructs candidates and plans from the pinned packaging selections and
original Git objects in a disposable directory. It then compares every planned
operation, URI, source hash and executable bit, target binding and index field.
Only absolute workspace coordinates are rebased for this comparison. Actual
candidate files are reobserved through the existing URIpack plan validator.

```bash
python3 tools/verify_repositories.py \
  --selection selections/repositories-v1.json \
  --package-source /path/to/uriprocess \
  --source runtime=/path/to/runtime \
  --source connectors=/path/to/connectors \
  --workspace /private/recovery/repository-plans \
  --out /private/recovery/repository-verification.json
```

The same explicit URIpack dependency and source paths as preparation are
required. Select the expected mapping through the trusted operator's own input;
the batch's `repository-selection.json` is compared with it, not selected as an
authoritative configuration by the tool. A passing check attests to agreement

### Apply a complete explicit batch

`tools/apply_repositories.py` executes already selected repository plans through
URIpack's actual `GuardBridge`. It exposes no synthetic Guard, self-approval,
automatic Strategy selection or Git publication option. Supply the expected
selection and sources exactly as for verification, plus one explicit
`--guard-config REPOSITORY=PATH` argument for every selected repository.

```bash
python3 tools/apply_repositories.py \
  --selection selections/repositories-v1.json \
  --package-source /path/to/uriprocess \
  --source runtime=/path/to/runtime \
  --source connectors=/path/to/connectors \
  --workspace /private/recovery/repository-plans \

  --guard-config uriprocess/ticket-readiness=/operator/protected/bridge.json \

  --guard-config uriprocess/credential-harvest=/operator/protected/bridge.json \
  --output /private/recovery/new-batch-evidence
```

The bridge path is an operator-provisioned placeholder. Sharing its configuration
still gives every plan a separate admission, lease/check sequence and completion;
it does not turn the batch into one broad grant. The output parent must exist,
and the output directory must be new and disjoint from the batch and all sources.

Before its first effect, the command independently verifies the complete batch,
reobserves every plan and constructs all eight real bridge clients. A missing
mapping, invalid final configuration, changed pin or occupied target prevents
all extraction. Bridge configuration and pinned implementation files must remain
outside every source and the complete batch, not merely outside one package.
The operator must protect the executable, dependencies, configuration and lease
store; a content hash alone does not establish OS-level isolation.

Successful execution writes private started/attempt/completed receipts and
`batch-extraction.json`, then proves the complete artifact readback with the
existing verifier. Receipt files use exclusive creation and mode 0600. It makes
no remote Git or package-registry write and no production routing change.

The first failure stops subsequent packages, writes a bounded `halted.json` and
returns nonzero. Preflight returns a structured diagnostic such as
`BATCH_GUARD_MAPPING_INCOMPLETE`, with `execution_started=false`. If evidence
storage fails after an execution attempt, `BATCH_EVIDENCE_UNAVAILABLE` instead
reports that effects may have occurred; it never labels that failure as an
unstarted preflight. Raw exceptions and bridge output are not copied into evidence.
An attempt marker without a completion record also survives abrupt process loss.
If local publication happened before a failed completion, URIpack preserves its
`MATERIALIZED_PENDING_COMPLETION` target. Existing targets are rejected on the
next invocation: their independent recovery belongs to the protected Guard
controller, not a blind retry or deletion by this tool. Read-only inspection is
available below. Resolution of unknown outcomes remains a separate protected
integration.

### Inspect an interrupted repository batch

`tools/inspect_repositories.py` observes every selected destination, including a
partially materialized batch. It first runs the same independent reconstruction
against the explicitly supplied selection and pinned upstream Git objects.
Changed source, plan or index bindings stop inspection before target readback.

```bash
python3 -B tools/inspect_repositories.py \
  --selection selections/repositories-v1.json \
  --package-source /path/to/uriprocess \
  --source runtime=/path/to/runtime \
  --source connectors=/path/to/connectors \
  --workspace /private/recovery/repository-plans
```

The JSON result goes to stdout. The tool creates no batch receipt and does not
modify the batch, targets, source repositories, application evidence or writer
state. Temporary upstream reconstruction is removed after verification. It
never calls Guard, applies a plan, retries an effect or removes a lock.

| Per-repository status | Local observation |
| --- | --- |
| `not_materialized` | No target entry was present in the initial directory inventory; this does not establish that a prior attempt had no effects. |
| `extracted_local` | Artifact files and executable modes match the pinned plan; the local receipt, checks and event chain are consistent with `EXTRACTED`. |
| `pending_completion` | Artifact and local receipt are consistent with `MATERIALIZED_PENDING_COMPLETION`; protected resolution remains outstanding. |
| `inconsistent` | The target, artifact or receipt cannot be verified, or the receipt changed during readback. Other selected repositories are still inspected. |

Receipt verification binds the plan, artifact and source hashes, copied-file
count, required check subjects, event order and local hash chain. A rehashed
receipt for another plan or artifact is rejected. These are local consistency
checks against the pinned URIpack executor format; they do not authenticate the
Guard identity or decision references. Even a fully forged but self-consistent
receipt cannot grant execution authority through this tool.

The observation also reports writer-lock presence and the number of matching
staging entries. It does not enter staging directories or read lock contents.
Symlinks and special receipt files are rejected by URIpack's no-follow reader.
The destination directory inventory is limited to 4096 direct entries; exceeding
that bound fails preflight. Unexpected entries are counted without copying their
names or contents into the result.

Pending completion, inconsistent targets, writer/staging state, unexpected
entries or an observed directory change produce `requires_reconciliation` and
exit code 2. Valid observations without those findings produce `observed` and
exit code 0, including an empty or partially extracted batch. Invalid preflight
produces a bounded `blocked` diagnostic and exit code 2. No status means that
migration or protected recovery has completed.

The result always retains `automatic_retry=false`, `execution_authority=false`,
`guard_receipts_authenticated=false`, `remote_publication=false` and
`production_cutover=false`. `observation_atomic=false` describes the actual
sequential readback: the tool compares directory metadata before and after the
scan and receipt bytes around artifact verification, but cannot exclude every
concurrent modification. Coordinate a quiescent observation with the writer
owner and use independent Guard recovery before deciding on further effects.
The separate batch application's journal is preserved but is not authenticated
or reconciled by this inspector.

Local validation on 2026-09-09 passed the complete 66-case Python suite with
no omitted cases, the 17 original POA tests and the existing Docker checks.
The eleven inspection cases cover empty, partial and complete extraction,
failed completion, artifact corruption, rehashed receipt binding changes,
malformed/missing/symlink/special receipts, preserved writer and staging state,
concurrent receipt and directory changes, pinned-source preflight and CLI
exit/status behavior. Tests use the existing synthetic test Guard only to
prepare real URIpack artifacts; inspection itself is checked to make no Guard
or apply calls. The pinned Docs checker and Platform artifact build/check also
passed; the latter still has no coverage entry for this repository.

## Limitations

The two runtime selections and six native connector packages are covered.
The `uriprocess/*` destinations are proposals: read-only GitHub API observation
on 2026-09-09 returned HTTP 404 for both the organization and user handle
`uriprocess`. Remote existence and access are unconfirmed; no destination
repository was created, published or transferred by this change.
Other `subactor/*` processes, capability DAG execution, production routing,
source removal and package registry publication are not established by these checks. The standalone
readiness adapter still rejects decisions requiring a trusted callback when
that callback is absent; an `execute` decision is not an execution grant.

No operational uripack GuardBridge configuration was supplied or identified in
the inspected standard configuration locations, and no matching Guard service
was listed by the inspected systemd instance. This does not exclude an external
deployment. Preparation, bridge extraction with a synthetic Guard, and native
export through a real disposable Guard server were executed. Operational
guarded extraction remains unverified. Do not substitute either test setup for
the protected production boundary.

The native Guard reference profile still exports only the original two POA
packages. The added Python packages have separate uripack extraction and wheel
evidence; they were not added to that Guard profile and have no Docker claim.
Platform process-pack declarations in other DSL formats are not converted into
Python or POA executors by these tools.

The remaining `subactor-twin-map` Python connector is not in this selection.
Its tests at the pinned connector revision reference `~/github/uri-twin/uri-twin-plesk`
and `~/github/urirun-connectors`, and skip conformance checks when those references
are unavailable. A portable extraction needs explicit pinned reference fixtures
and validation context before it can satisfy the no-skips check. Source copying
alone would not establish its conformance.

The Platform artifact registry has no entry for this repository. Its build and
check do not register or validate this document; the pinned Wellmanifest Docs
checker is the applicable local documentation check. Local validation does not
establish independent CI, merge, deployment or fleet-wide adoption.
